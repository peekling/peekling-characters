# Oficjalne pakiety postaci Peekling

Poznaj małe postacie, które nadają Peeklingowi jego wyjątkowy charakter.

To oficjalne repozytorium pakietów postaci tworzonych i utrzymywanych przez projekt Peekling. Każdy pakiet opisuje wygląd, ruchy i reakcje postaci oraz sposób, w jaki przedstawia się ona zgodnemu środowisku wykonawczemu Peekling. Pakiety są otwartoźródłowe, zawierają wyłącznie dane i mają niezależne wersje.

Odwiedź [organizację Peekling](https://github.com/peekling) lub przeczytaj [przewodnik tworzenia pakietów](../PACK-AUTHORING.md), aby zobaczyć, jak zbudowana jest postać.

## Co to jest pakiet postaci?

Pakiet postaci to niewielki zestaw danych i obrazów. Nie zawiera wykonywalnego kodu sterującego zachowaniem postaci.

Każdy oficjalny pakiet zawiera:

- manifest `character.json` z tożsamością postaci, stanami, ruchem, wersją i licencją
- atlasy PNG w skalach 1x, 2x i 4x dla różnych gęstości wyświetlania
- podgląd `thumbnail.png`
- własne `README.md`, `LICENSE` i `NOTICE`

Manifest rejestruje bezpieczne względne ścieżki obrazów i skróty SHA-256 dla każdego atlasu. Skrypty programistyczne, testy, grafika źródłowa i wygenerowane raporty kontroli jakości pozostają w tym repozytorium i poza granicami opublikowanego pakietu.

## Korzystanie z pakietu

Gdy postać pojawi się w tabeli, użyj łącza jej pakietu, aby przejść do zweryfikowanej wersji dostępnej w npm. Katalog źródłowy opisuje polecenie walidacji i dokumentację licencyjną, a `character.json` pozostaje głównym źródłem informacji o stanach, ruchu, grafice i możliwościach postaci.

Tylko wiersze z łączem do npm zostały zweryfikowane jako możliwe do zainstalowania. Wiersz `(niewydane)` wskazuje kod źródłowy w repozytorium do dalszej pracy i nie jest deklaracją dostępności. Katalogi źródłowe mogą też zawierać zmiany nowsze niż wersja w npm. Środowisko wykonawcze Peekling jest oddzielone od tych pakietów postaci i odpowiada za wczytanie manifestu oraz wyrenderowanie wskazanego atlasu.

Obszar roboczy w katalogu głównym repozytorium jest prywatny i nie można go opublikować. Granicami wydań są wyłącznie poszczególne obszary robocze `packages/pack-*`.

## Stwórz postać

Masz pomysł na nowego małego przyjaciela? Kreatywny rdzeń pakietu składa się z trzech części:

- `character.json` opisuje postać, jej stany animacji, ruch, wersję, licencję i pliki atlasu.
- `atlas-1x.png` to minimalny atlas graficzny w umowie ogólnej pakietu. Oficjalny pakiet musi również zawierać pasujące warianty `atlas-2x.png` i `atlas-4x.png`.
- `thumbnail.png` to mały podgląd pokazywany w galeriach i na listach pakietów.

Oficjalny pakiet gotowy do publikacji wymaga również plików `package.json`, `README.md`, `LICENSE` i `NOTICE` oraz wszystkich atlasów wymienionych w manifeście. Zacznij od [przewodnika tworzenia pakietów](../PACK-AUTHORING.md) i użyj [pakietu Peek](../packages/pack-peek) jako kompletnego przykładu źródłowego.

Gdy zaawansowane narzędzia do tworzenia zostaną wydane, pojawią się tutaj odpowiednie łącza. Do tego czasu źródłem informacji są przewodnik tworzenia pakietów, manifesty i aktualne oficjalne pakiety.

## Współtworzenie

Przemyślane poprawki i ukierunkowane ulepszenia są mile widziane. Jeśli chcesz zaproponować nową oficjalną postać lub większą zmianę, najpierw [otwórz problem](https://github.com/peekling/peekling-characters/issues), abyśmy mogli uzgodnić zakres, pochodzenie grafiki i licencję.

Będziesz potrzebować Node.js 22 lub nowszego. Obszar roboczy rejestruje npm 11.19.0 jako menedżera pakietów.

1. Otwórz problem dla nowej postaci, aby omówić jej nazwę, miejsce w oficjalnej kolekcji, własność grafiki i licencję, zanim wykonasz dużo pracy. Zmiany w istniejącym pakiecie są akceptowane dopiero po zatwierdzeniu ich przez właściciela kodu lub wyznaczonego recenzenta.
2. Utwórz fork i sklonuj repozytorium, a następnie zainstaluj zależności obszaru roboczego za pomocą `npm install`.
3. Wybierz nowy identyfikator zapisany małymi literami, np. `my-friend`. Nie może powielać katalogu postaci, nazwy manifestu ani pakietu npm. Użyj [kompletnego pakietu źródłowego Peek](../packages/pack-peek) jako przykładu strukturalnego i utwórz `packages/pack-my-friend`.
4. Utwórz granicę do opublikowania:

   - `package.json` nazywa `@peekling/pack-my-friend`, deklaruje wersję semantyczną, publiczny dostęp, licencję, katalog repozytorium, skrypty kompilacji i testowania oraz dokładne pliki publiczne.
   - `character.json` używa formatu 1 i tej samej nazwy, wersji i licencji. Nadaj mu tytuł, autora, opis, rekordy atlasowe 1x/2x/4x, stany animacji z prawidłowymi klatkami i synchronizacjami, wszystkie osiem kierunków ruchu i dodatnią skalę domyślną.
   - `thumbnail.png` to prawidłowy 64x64 PNG. Obecna oficjalna siatka wykorzystuje 64-pikselowe komórki logiczne, 16 kolumn i 3 rzędy, więc trzy atlasy to 1024x192, 2048x384 i 4096x768. Ich deklarowana gęstość, rozmiar komórki, wymiary i skróty SHA-256 muszą się zgadzać.
   - Dodaj `README.md`, `LICENSE`, `NOTICE`, test ukierunkowany i każdy atlas, do którego odwołuje się manifest. Trzymaj grafikę źródłową i pomocników programistycznych poza listą `files`.
   - W przypadku bieżącego procesu tworzenia grafiki ręcznej dodaj postać do `scripts/build-character-roster.mjs` wraz z wymaganymi metadanymi i zapisami ruchu. Dostarcz te same dane źródłowe przeznaczone tylko do repozytorium, używane przez istniejące pakiety, aby `npm run build` mógł odtwarzać atlasy, zamiast akceptować ręcznie edytowane dane wyjściowe.

5. Uruchom test i kompilację ukierunkowanego pakietu. Dla Peek równoważne polecenia to:

   ```sh
   npm test -w @peekling/pack-peek
   npm run build -w @peekling/pack-peek
   ```

6. Jeśli metadane pakietu uległy zmianie, wygeneruj ponownie tę tabelę za pomocą `npm run roster`, a następnie uruchom pełną bramę repozytorium za pomocą `npm run check`.
7. Uruchom `npm run changeset` i uwzględnij każdy pakiet, którego to dotyczy. Każda zmiana pliku w katalogu pakietu wymaga decyzji dotyczącej wersji, w tym grafiki, JSON, metadanych, dokumentów, testów i plików źródłowych. Sam wybierz poziom:

   - `patch` dla kompatybilnych poprawek, poprawek lub dostrojeń
   - `minor` dla znaczących dodatków kompatybilnych wstecz lub istotnych aktualizacji kreatywnych
   - `major` w przypadku niezgodnej wstecz zmiany, zastąpienia lub usunięcia

   Automatyzacja nigdy nie zgaduje poziomu na podstawie rozmiaru lub rodzaju zmiany.

8. Otwórz pull request opisujący postać, pochodzenie i licencję grafiki, zakres zmian oraz uzasadnienie wybranego poziomu wersji.

Przed przeglądem CI pull requestu wymaga planu wydania dla każdego zmienionego pakietu. Następnie sprawdza kontrakt manifestu i definicje stanów, unikalność identyfikatorów, dostępność nazw npm dla nowych pakietów, bezpieczne ścieżki obrazów i skróty, integralność plików PNG, rozmiar miniatury, obecność atlasów 1x/2x/4x i geometrię skalowania, testy, powtarzalne kompilacje, limity rozmiaru, licencje oraz dokładny zestaw plików w każdym testowym pakiecie npm. Kontrole te zapobiegają przypadkowym konfliktom i błędom pakowania. Recenzenci nadal decydują, czy postać lub zmiana należy do oficjalnej kolekcji.

Gdy zatwierdzona zmiana trafi do `main`, Changesets przygotuje osobny pull request z wersjami do przeglądu. Pierwsza publikacja w npm pozostaje świadomym działaniem opiekuna. Automatyczne publikowanie przez OIDC można włączyć dopiero po utworzeniu pierwszych pakietów i skonfigurowaniu zaufania do procesu publikowania tego repozytorium. Do zakończenia tej konfiguracji kod źródłowy w repozytorium nie gwarantuje dostępności pakietu w npm. Pełny proces opisano w dokumencie [przygotowanie wydania](../RELEASING.md).

To repozytorium jest wyselekcjonowanym zbiorem oficjalnych pakietów Peekling, a nie globalnym katalogiem społeczności. Twórcy mogą publikować zgodne pakiety innych producentów we własnych pakietach lub serwisach hostingu statycznego, pod warunkiem użycia ważnej licencji publicznej.
